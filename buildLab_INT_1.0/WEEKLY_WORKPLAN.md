# 24-week, five-day workplan

Each month has four weeks. Each week has five working days. All four teams follow the same cadence and adapt the deliverable to their current team assignment.

## Daily cadence

| Day | Focus | Required output |
| --- | --- | --- |
| Monday | Learn, plan, clarify acceptance criteria | Personal goal, team goal, risk/blocker list |
| Tuesday | Build or design | Working draft, code, test, research, or customer artifact |
| Wednesday | Integrate with another track | Review request, API/design contract, or paired work |
| Thursday | Test, refine, document | Evidence, defect/finding list, updated artifact |
| Friday | Demo, review, retrospective | Demo, progress update, case-study evidence, next action |

## Week-by-week learning and product outcomes

| Week | Learning focus | Shared product outcome |
| ---: | --- | --- |
| 01 | Orientation, Git/GitHub, tools, team roles | Product brief, local setup, repository rules |
| 02 | Users, stakeholders, accessibility, discovery | Personas, assumptions, success metrics |
| 03 | User journeys, requirements, information architecture | Login and task journeys, initial backlog |
| 04 | Track fundamentals and review practice | Month 1 demo and two case-study drafts per team |
| 05 | Design tokens, coding standards, test language | Shared conventions and review checklist |
| 06 | Data modeling, API contracts, wireframes | Approved schema, endpoint contract, wireframes |
| 07 | App shell, environments, test setup | Running foundation for the vertical slice |
| 08 | Authentication and protected flows | Auth design/API/UI/test evidence |
| 09 | Vertical-slice implementation | Login plus one task flow works end to end |
| 10 | Negative paths, accessibility, API validation | Failure, permission, keyboard, and API coverage |
| 11 | Integration review and defect fixing | Repeatable demo by another team member |
| 12 | Checkpoint and release discipline | Development milestone and Month 3 case studies |
| 13 | Teams, roles, permissions | Team and role behavior across UI/API/tests |
| 14 | Task CRUD and validation | Create, edit, assign, and reject invalid tasks |
| 15 | Search, filters, status, pagination | Usable list behavior and edge-case coverage |
| 16 | Notifications and responsive states | Mobile, empty, loading, error, success states |
| 17 | CI, linting, formatting, build checks | Pull requests run automated quality checks |
| 18 | Regression, integration, and test stability | Critical journey regression suite |
| 19 | Staging deployment and migrations | Repeatable staging release |
| 20 | Security, logs, metrics, incident response | Health checks, runbook, and recovery drill |
| 21 | Performance, reliability, cost | Measured improvement and risk report |
| 22 | Release candidate and accessibility pass | Release checklist, rollback plan, known issues |
| 23 | Final release and portfolio evidence | Release notes, demo recording, case-study pack |
| 24 | Handoff and retrospective | Final presentation, runbook, and individual reflection |

## Weekly completion rule

A week is complete only when the team has:

- one merged or reviewed product artifact;
- one test, design, operational, or customer-facing evidence item;
- one Friday demo/update;
- updated individual `W-XX/README.md` files; and
- an owner and next action for every unresolved blocker.
