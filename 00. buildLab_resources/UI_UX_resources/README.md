# UI/UX and product design track

## Mission

Design a usable, accessible, and developer-ready Team Management Platform. A successful designer explains the user problem, tests assumptions, creates reusable components, and hands off decisions clearly. Visual polish is important, but it is not a substitute for evidence.

## Six-month progression

| Month | Learn and practice | Product deliverable | Validation |
| --- | --- | --- | --- |
| 1 — Discover | User interviews, personas, jobs-to-be-done, assumptions, accessibility basics, Figma foundations | Product brief, two personas, login and task user journeys | Interview guide, research summary, mentor critique |
| 2 — Structure | Information architecture, task flows, wireframes, content hierarchy, responsive thinking | Sitemap, user flows, low-fidelity wireframes | Walkthrough with a non-designer; revise from feedback |
| 3 — Define | Visual hierarchy, grids, spacing, color, type, tokens, components, variants, auto layout | Design foundations and clickable login-to-task prototype | Contrast check, keyboard-flow review, developer handoff |
| 4 — Design features | Forms, tables, filters, status, permissions, notifications, empty/loading/error states | High-fidelity team and task-management screens | Cross-track design review; all states represented |
| 5 — Test and refine | Usability testing, iteration, responsive behavior, content quality, design QA | Usability test report and revised prototype | At least five test participants or peer sessions; prioritized findings |
| 6 — Ship and document | Design QA, release notes, case study writing, portfolio presentation | Final design library, annotated flows, case study, handoff pack | Final critique; another designer can reuse components |

## Weekly practice

- Weeks 1–4: observe users and reproduce one existing product flow in Figma.
- Weeks 5–8: turn the product brief into flows and wireframes; document assumptions.
- Weeks 9–12: build token and component foundations; prototype one vertical slice.
- Weeks 13–16: design team, task, search, filter, and permission states.
- Weeks 17–20: run usability and accessibility reviews; fix the highest-risk issues.
- Weeks 21–24: complete design QA, handoff, release documentation, and portfolio evidence.

## Required outputs

1. Research notes and assumptions log.
2. Sitemap and user flows.
3. Wireframes and high-fidelity screens.
4. Variables/tokens, components, and variants.
5. Prototype with realistic content.
6. Accessibility and usability findings.
7. Developer handoff and design QA checklist.
8. One case study: problem, process, decisions, result, and learning.

## Design review checklist

- Is the primary user and task clear?
- Does each screen have a useful hierarchy and a single primary action?
- Are loading, empty, error, success, disabled, and permission-denied states defined?
- Can the flow be completed with keyboard and assistive technology?
- Are labels, validation messages, and button names understandable without color alone?
- Are components reusable instead of copied screen by screen?
- Can a developer implement the design without guessing behavior or content?

## Final assessment

Present a five-minute case study and a ten-minute prototype walkthrough. Trace each major design decision to user evidence, a product requirement, or an accessibility concern.
